PDDL authoring: what the screens should look like

Six concept mockups for the next phase of the authoring tool. They follow one decision: people edit through guided sentences and dropdown menus, and use the graph to find their way around a domain — not to build one.

The direction being proposed

Dropdowns for writing. Graphs for finding.

The research paper found the same result in every published evaluation of visual PDDL tools: building a domain by dragging boxes and wires is slower than typing, and it does not make the vocabulary any easier for a non-specialist. What people actually struggle with is different in each case — an engineer cannot find anything in a domain of sixty actions, and a non-engineer does not know what "delete effect" means. Those need two different answers, so the concepts below split the tool along that line.

Editing Guided sentences

Every slot is a dropdown holding only the choices that are legal at that point. A type error becomes impossible to express rather than something reported afterwards.

Navigation Small, computed views

Never the whole domain at once. One element plus its immediate neighbours, with back and forward history — plus a matrix and per-type lifecycle diagrams for overview.

Escape hatch The PDDL stays real

The PDDL tab remains editable and round-trippable through the existing importer. For an experienced engineer, typing stays the fastest path, and that is fine.

One colour language throughout: requires makes true makes false
WI-6.4 Primary editing surface

Guided action editor

This replaces the current selected-element panel. The action is described as three plain-English sentences — what it involves, what must be true before, and what changes afterwards. The words "precondition", "add effect" and "delete effect" never appear on screen. Every bracketed slot is a dropdown, and each dropdown is filtered to what the type system allows in that position.

WI-6.3 What the canvas becomes

Focused neighbourhood view

The current canvas draws every predicate in one row and every action in another, joined only by hand-drawn links that the PDDL generator ignores. This replaces it: the selected element in the middle, everything one step away around it, nothing else. Positions are computed, so nobody has to tidy the layout by hand as the domain grows. Clicking a neighbour re-centres the view on it.

DomainView neighbourhood · 1 step
Around (task-assigned ?s ?a) ◀ ▶ steps: 1 show: everything Whole domain A

  • ADepth control, a filter for which relationship kinds to draw, and an explicit escape to the existing whole-domain canvas for small domains or for a presentation slide.
  • BBecause the subgraph is computed, layout is computed too. The stored posX/posY fields stop being something a user has to maintain.
  • CHeavily used facts such as (at ?a ?l) would flood the view, so neighbours are capped and the remainder collapses into a single "+ n more" node that opens a list.
  • DEvery edge here is derived from the model, not drawn by hand. That removes the reason causalLinks exists — see the closing section.
What it fixesThe wall of nodes. Domain size stops affecting readability.
CostMedium — an index, a small layered layout routine, history. No new library.
Depends onWI-6.1. Uses the imgui-node-editor already integrated.
WI-6.5 Overview without a graph

Fact-by-action matrix

For a wide, shallow domain a grid is often more readable than any graph, and it exposes gaps immediately. Below is the real mission-autonomy domain. Two things jump out of it that are hard to see in the PDDL file itself, and both are called out under the table.

What this view already tells us about the real domain

comms-available is required by reallocate-task and is never made true by anything. If a scenario does not start with it, reallocation can never happen — which is exactly the behaviour the comms-lost contingency problems rely on, but nothing in the file says so out loud.

classified has exactly one action that makes it true and no action that ever makes it false. Any goal mentioning it depends on a single action succeeding, so a reviewer looking for single points of failure should start there.

Four facts in total — agent-available, sensor-operational, sensor-degraded and comms-available — are required by actions but produced by none. Each is set once in the scenario file and never changes again, which is a deliberate modelling choice here and worth stating explicitly rather than leaving for a reader to infer.

What it fixesReviewing a whole domain at once, and spotting facts nothing changes.
CostLow. An ImGui table over the same index.
Depends onWI-6.1.
WI-6.6 The domain, sliced by type

Object lifecycle view

A domain is wide because it describes several kinds of thing at once. Split it by type and each slice becomes a small state diagram — the kind of picture a systems engineer can read without any planning background. A domain that is unreadable as one large picture is usually readable as several small ones.

DomainView lifecycles · 2 of 3 types grouped
agent 2 objects grouped by: availability
sector 3 objects grouped by: task state
groupings declared by hand · automatic suggestion is a later step A
  • AThe first version asks the user to say "these facts are alternative states of an agent" and stores that grouping in the project. Working it out automatically is a later addition, not a prerequisite.
  • BBoth diagrams here were drawn from the real domain, and both surfaced something worth a review question — an agent that can never recover, and a sector that can never be re-searched. Neither is visible in the PDDL at a glance.
  • CSensor state has no diagram because no action changes it; sensor-degraded is only ever set in the scenario file. The view showing nothing is itself the correct answer.
What it fixesReviewability. Eight small state diagrams instead of one unreadable picture.
CostMedium. Higher if automatic grouping is attempted — so stage it.
Depends onWI-6.1 plus one new field on the project model for groupings.
WI-6.8 The message that decides whether people keep using the tool

§4.2 · WI-6.10 Deliberately left out

What these concepts do not propose

Not now Snap-together blocks

Scratch-style blocks suit tree-shaped logic — nested and, or, not. AME's PDDL support is flat conjunctions today, so blocks would buy nothing a dropdown does not already give. Revisit if nested conditions arrive; reimplement the interaction in ImGui rather than embedding a browser for Blockly.

Not at all Graph-first authoring

Building a domain by wiring nodes together. Every published evaluation that measured it found it slower than typing, and it does not help the people it is meant to help. The graph earns its place as a way to look, not a way to write.

Decision needed Hand-drawn causal links

causalLinks is drawn, saved and type-checked today, and then read by nothing — not the PDDL generator, not the planner. The neighbourhood view derives the same relationship automatically, so the field should become derived and read-only, or be removed.

Suggested build order

Each step is useful on its own

One shared piece comes first — an index answering "which actions need, make true, or make false this fact". Five of the six concepts above are a panel over that index. Nothing here invalidates code already written, and no new third-party dependency is needed.

For this review

Questions these mockups are asking

  1. Is the sentence wording right for your users?
    "Before it can happen" and "Afterwards" are the two labels doing the most work. If the people who will use this say "entry conditions" and "outcomes", the mockup should say that instead — the words are cheap to change now and expensive later.
  2. Does the guided editor come before or after the navigation work?
    The research recommends the index and relations panel first, because everything else reads them. If the immediate audience is non-specialists rather than engineers, the guided editor could go first — it depends on nothing new.
  3. Should the whole-domain canvas survive?
    These concepts keep it as an explicit "show everything" mode. If nobody wants it, dropping it removes the stored positions, the hand-drawn links and a chunk of code.
  4. Is the fact-by-action matrix a review artefact in its own right?
    It found two real properties of the mission-autonomy domain while these mockups were being drawn. If it is going into assurance evidence, it needs an export format, which is a small addition worth deciding now.

Simulation runs: what the screens should look like

Six concept mockups for the next phase of the authoring tool. Today it can tell you a plan exists and show you the tree it compiled. It cannot show you that tree running. These screens are how it would.

The direction being proposed

Watch the mission, not the machinery.

A run is the first thing in this tool that a non-specialist can judge without being taught anything: either the mission does what they expected or it does not. That only holds if the screens talk about the mission. The moment they talk about ticks, node status codes and replanning episodes, the advantage is gone.

Rule 1 Say what is happening

A run always has a one-sentence answer to "what is going on now", in the words of the mission: uav2 is moving from base to sector_b. The tree and the timeline are how you check that sentence, not how you work it out.

Rule 2 Nothing to set up first

Pressing Run works on a project that has never been near this screen. Every action takes four ticks, which is one second at the speed shown above, and succeeds until somebody says otherwise. Settings exist for people who want a specific fault, or an action whose duration matters to the mission, not as a toll on the first run.

Rule 3 A simulation is never evidence of field behaviour

The real compiled tree, the real world model and the real planner are used. Only the action nodes are stand-ins, and the screen says so, every run, where it cannot be missed. The tool never lets a run look like a test flight.

Something drawing this surfaced, and it settles a design question.

The four facts offered for mid-run change are exactly the four that no action in this domain ever makes true: comms being available, an agent being available, a sensor working, and a sensor having failed. The earlier concept pack found them while drawing the failure report, where they showed up as a gap. They are not a gap. They are the domain's boundary — the things that happen to the mission rather than because of it, which is why the domain sets them once in the scenario and never touches them again.

That is the argument for putting fault injection at run time rather than modelling it as actions the planner could choose. It also gives the control an honest default: offer the facts nothing produces first, because those are the ones a run cannot otherwise reach.

What it fixesContingency actions can be checked by reading them, and nothing else.
CostPart of B4. The controls are small; the replanning behind them is not.
Held toTwo mechanisms, fixed now. Anything more expressive is a separate decision.
B4 · part 2 Concept 4 of 6

When the mission changes course

This is the screen the whole workstream exists for, and the hardest to word. Something went wrong, the planner produced a different plan, and the tool has to explain that to someone who has never heard the word "replan". The proposal: say what happened, say what it costs, and show the two plans side by side with the change marked.

B6 · B7 Concept 6 of 6

Runs you can keep, send and compare

Every run is recorded to the three files the runtime already writes, in the same formats. DevEnv's replay loader reads exactly those three, so a run recorded here opens there with no conversion — and a run recorded from a real system opens here, in the timeline from concept 2. Comparing two runs is then a small addition with a large payoff: it is how a user finds out what their change did.

What these concepts do not propose

Not at all A language for faults

Two mechanisms, fixed now: make an action fail on a given attempt, and set a fact at a given tick. Fault scripting grows one reasonable request at a time until the tool has a second modelling language nobody asked for.

Not at all Real time, or real timing

Ticks are ticks. A run says an action took five ticks, never five seconds. Anything that looks like a duration invites someone to read a schedule out of it, and this tool has no basis for one.

Not at all A live connection

Simulation is in-process against the world model, with no transport involved. Watching a real system remains DevEnv's job. The two meet in the recorded files, not on a wire.

Not now Editing during a run

Changing the domain mid-run raises questions about what the running tree then is. Hold, edit, start again — three deliberate steps rather than one ambiguous one.

Not now A map

Sectors and locations are names, not places. A picture of two vehicles moving over terrain would be the most persuasive screen in the tool and would be showing spatial information the model does not contain.

Decision needed Where the Run tab lives

These mockups add a sixth tab. The alternative is that the existing BT tab gains the controls and becomes the run view. Fewer tabs, but it merges "the tree you compiled" with "the tree that is running". See Q4.

Suggested build order

Each step is useful on its own

One piece comes first and everything else reads it: an engine that ticks the compiled tree against the world model and reports what happened. Five of the six concepts above are a view over that event stream. No new third-party dependency is needed, and nothing here invalidates code already written.

For this review

Questions these mockups are asking

These are the decisions that are cheap now and expensive once the screens exist. The first three are the ones the plan committed to asking.

  1. Are these the right words for the run controls?
    The mockups use Run · Hold · One step · Stop · Start again. The machine words would be Play, Pause, Tick, Stop, Reset. "Hold" and "Start again" are the two doing the most work, and they are the two most likely to be wrong: if the people who will use this say "pause" and "reset" in their own speech, the mockups should say that instead.
    Answered in reviewThe ordinary machine words. The people who use this are technical, just not software engineers, and they say “pause” and “reset” in their own speech. The controls are Run · Pause · Step · Stop · Reset. Built.
  2. Is the timeline the primary view, or the tree?
    These mockups lead with the tree because it is what the tool already draws, and put the timeline second. Drawing them argued the other way: two agents working at once is invisible in the tree and obvious on the timeline, and "when did that happen" is the question a reviewer actually asks. Swapping them is cheap now and awkward later.
    Answered in reviewThe timeline. The tree stays, beside it, as the answer to “where are we” rather than as the thing a reviewer reads first. Not built yet: the run screen currently leads with the tree, and the timeline takes the primary position when B3 lands.
  3. How should a change of plan be announced?
    The proposal is "the mission has taken a different route", with the cause above it and the cost beside it, and the word "replan" nowhere on the screen. The risk is that people who do know the term now have to translate. An alternative is to lead with the plain sentence and put the technical term in the run record and the exported report, where the audience is different.
    Answered in review“Replan” is fine on the screen, for the same reason as the control names. The plain sentence is still worth having; it no longer has to avoid the word.
  4. A sixth tab, or does the BT tab become the run view?
    A separate Run tab keeps "the tree you compiled" and "the tree that is running" apart, at the cost of two tabs showing the same tree. Folding them together is tidier and makes the compiled tree feel like a thing that runs rather than a thing you inspect. This is a layout decision, but it changes what the tool appears to be for.
    Answered in reviewThe BT tab becomes the run view. There is no separate tree tab: the Run tab draws the compiled tree, waiting when nothing is running and coloured as it goes when something is. Built.
  5. Should a simulated run and a real run look identical?
    Concept 6 puts a run recorded from the vehicle in the same list, in the same timeline, with the same controls, and distinguishes them only by the SIMULATED warning and a label on the row. That is either the point — one way of reading a mission, whatever produced it — or it is a confusion waiting to be quoted out of context in a report.
    Answered in reviewThey look the same and the data says which is which. Every run this tool produces carries a simulated marker in its report and its record, so anything quoting a run has that to quote. Built for the report; the recorded runs follow in B6.
  6. Are two fault mechanisms enough to check this domain's contingencies?
    Failing an action and setting a fact mid-run cover every contingency path in mission-autonomy, because the four facts the domain never produces are exactly the levers those paths turn on. Whether that holds for the domains you have in mind is worth checking now: if it does not, the gap is a third mechanism, and it should be named before B4 starts rather than after.
    Answered in reviewYes. Failing an action and setting a fact mid-run are adequate; no third mechanism is planned, and B4 builds exactly these two.
